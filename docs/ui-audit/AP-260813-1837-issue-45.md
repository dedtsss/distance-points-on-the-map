## 2. Current UI map

Текущая оболочка — тёмный CRM-style AppShell: desktop sidebar, TopBar с progress, content area, footer; на mobile sidebar превращается в drawer. В `APP_SCREENS` сейчас восемь верхнеуровневых пунктов:

| Screen | Роль сейчас | Основные данные/состояния |
| --- | --- | --- |
| Dashboard | Обзор и быстрый вход в обработку | счётчики сессий/фото/точек, последняя сессия, issues |
| Sessions | История и поиск сессий | local/D1 records, поиск по номеру/названию/цвету/упаковке/status |
| Upload | Рабочая сессия: файлы, настройки и запуск pipeline | stable files, folder import, OCR/cleanup/upload, progress, PhotoCard |
| Reserve | Отдельный список RESERVE | возврат в ACTIVE, открытие сессии, карта |
| Map | Географическая проверка | Leaflet, слои, ACTIVE/RESERVE, фильтры, conflicts |
| Results | Итог и экспорт | metrics, filters, desktop table, mobile cards, exports |
| Journal | Диагностика процесса | OCR summary, per-photo details, event timeline |
| Settings | Глобальные настройки и storage diagnostics | metadata, OCR, map, threshold, upload providers, export text, clear |

Связка stage/screen сейчас неполная: `processing` и `upload` открывают один экран Upload, `map` — Map, `result` — Results. Поэтому визуальный wizard из четырёх шагов не соответствует четырём отдельным экранам: большая часть действий всех этапов остаётся на одном длинном Upload screen.

CRM-shell работает, но одновременно показывает два уровня уведомления при недоступном сервере: error о несинхронизированной сессии и banner о недоступном server storage. Это технически полезно, но визуально дублирует одну проблему.

## 3. Current Session/Photo flow

1. Пользователь создаёт draft session или нажимает `Новая сессия`, задаёт название, цвет, тип упаковки и описание.
2. Выбирает отдельные изображения через file input, папку через `webkitdirectory`/directory handle или drag-and-drop. Система создаёт stable-file entries, thumbnails и folder report; originals остаются локально до разрешённого pipeline.
3. На Upload screen доступны независимые команды `Только OCR`, `Очистить metadata`, `Загрузить очищенные` и `Полная обработка`.
4. Pipeline выполняет GPS metadata-first, multi-pass OCR fallback, индекс OCR, sanity/quality/conflict checks, optional metadata cleanup и upload только очищенных generic-файлов через same-origin API/provider chain.
5. Progress показывает общее состояние и per-photo status. PhotoCard даёт просмотр, редактирование индекса, ручную коррекцию координат, swap lat/lon, карту, share point, ACTIVE/RESERVE и удаление.
6. После OCR координаты и quality видны в карточках; `Map` показывает точки и conflicts, RESERVE остаётся видимым, но не участвует в конфликтном расчёте.
7. `Results` показывает summary, фильтры, таблицу на desktop и PhotoCard на mobile, копирование/экспорт индексов, координат, ссылок, GPX/KML/GeoJSON/TXT.
8. Сессия сохраняется локально и пытается синхронизироваться с D1. При отсутствии remote backend UI продолжает работу локально и помечает record как unsynced; restore после reload не обещает исходные source blobs.

Критичный UX-разрыв: wizard предлагает четыре шага, но step navigation не блокирует будущие шаги по prerequisites, а текущая рабочая поверхность и все pipeline actions остаются на шаге `Сессия и фото`. Пользователь может перейти к пустому Map/Results и затем возвращаться к длинной форме.

## 5. Дубли, stale и confusing actions

- `Полная обработка` есть в Dashboard, в Upload action grid и как очевидная цель wizard. Оставить одну primary command внутри active session; Dashboard должен только открыть/продолжить session.
- Выбор фотографий повторяется в Dashboard header, Dashboard quick action, UploadDropzone и empty state. Оставить разные entry points, но один label и одну semantics.
- Очистка представлена `Очистить результат`, `Очистить текущую сессию` и опасным действием в Settings. Оставить одно контекстное destructive action с явным scope и Settings как аварийный fallback.
- `ResultsTable` и mobile `PhotoCard` — допустимый responsive split, но action parity не совпадает: table имеет `Фото/Карта/Ссылки`, card — details/share/reserve/delete и ручные поля. Нужна единая action model с разным layout.
- `ErrorState`, `PhotoPicker`, `PhotoResultCard`, `ProcessingJournal`, `SectionHeader` — не импортируемые legacy-компоненты. Они дублируют текущие `EmptyState`, UploadDropzone, PhotoCard/ResultsSummary, Journal и PageHeader; их следует удалить только после проверки истории/coverage.
- `Внешний скрипт — скоро` и `Перенести — скоро` выглядят как рабочие actions, хотя действия не готовы. Их следует убрать из основной композиции или заменить явной roadmap/feature note вне action group.
- Два remote-unavailable сообщения следует объединить в один banner с состоянием `локально сохранено / синхронизация ожидает / повторить`.
- `Открыть карту` на Dashboard и `На карте` в PhotoCard сохраняются как контекстные действия, но должны вести к одной точке и одинаково сообщать отсутствие координат.

## 6. Mobile/responsive findings

Наблюдения подтверждены свежими 390 px captures:

- Dashboard масштабируется без заметного горизонтального overflow, но все четыре stat cards становятся длинным вертикальным стеком.
- Drawer занимает около 320 px из 390 px; длинный пункт Upload переносится на две строки. В закрытом состоянии drawer остаётся в DOM/accessibility tree и скрывается transform-ом; нет явных focus trap/focus return/`aria-modal`.
- Upload screen после выбора двух фото превращается в очень длинную последовательность: wizard, metadata fields, dropzone, четыре pipeline actions, progress и две PhotoCard. Primary action не закреплён в нижней safe-area action bar; прокрутка до следующего шага дорогая.
- Длинный TopBar title `Обработать фотографии · Загрузка и проверка` переносится и конкурирует за высоту с notices.
- Results mobile хорошо избегает desktop table, но summary, exports, textareas, filters и PhotoCards образуют длинный action-heavy экран. Ссылочные/export действия нужно свернуть в grouped menu/bottom sheet.
- Map side panel на mobile ограничен примерно `36vh`; после `Показать точки` одновременно видны только часть selected card и список. Нужны drag handle, явный `Развернуть`, отдельный full-screen details state и один scroll owner.
- Settings и Journal читаемы, но чрезмерно длинны: много самостоятельных controls и диагностических строк в одном scroll context. Нужны collapsible groups и summary of changed settings.
- Map legend/filter chips используют горизонтальные ряды; нужен явный scroll affordance и keyboard/touch test.
- Sticky TopBar визуально перекрывает/съедает notices на Map/Reserve/Settings/Journal; верхний safe offset должен быть единым.
- В текущем capture горизонтальный overflow не обнаружен. Это не заменяет проверку zoom, keyboard, TalkBack, real touch, Android picker и low-memory.

Положительное: touch targets в основных кнопках достаточно крупные, status/progress/error states видны, mobile result cards не требуют горизонтальной таблицы, а viewer поддерживает close/zoom/fit и touch gestures.

## 7. Functions and dependencies to preserve

Нельзя ломать при UI migration:

- `runPhotoPipeline` и порядок GPS metadata-first → OCR fallback → index OCR → quality/sanity/conflict → cleanup → upload.
- Privacy boundary: не отправлять originals/raw metadata; upload только очищенных generic-файлов через same-origin `/api/upload` и существующий Worker/provider policy.
- Stable-file store, thumbnails, folder picker capability detection, directory input/handle fallback, cancellation и folder report.
- Manual index/coordinate edits, coordinate confirmation, lat/lon swap, distance recalculation, confidence/low-precision/suspicious statuses.
- ACTIVE/RESERVE semantics и conflict resolver: RESERVE видим на карте, но не участвует в расчёте conflicts.
- Leaflet map model, tile layer IDs, marker identity, selected point, filters, recommendations and map viewport behavior.
- Local session store, D1 adapter/API contract, session migration, immutable numbering, local fallback, unsynced status and restore/delete semantics.
- Provider validation, fallback ordering, progress events, upload error classification and no-provider-links blocker.
- Exports/link formatting: index-coordinate rows, GPX/KML/GeoJSON/TXT, session share and copy operations.
- Journal/debug events, per-photo progress dataset consumed by TopBar/mobile progress.
- Settings persistence, threshold limits, region mode, export description and destructive clear confirmation.

Ant Design/ProComponents migration must be presentation-only at first. Do not replace domain modules, storage adapters, provider policy, pipeline, Leaflet model or file/privacy boundary as part of UI pilot.

## 8. Proposed information architecture

Предлагаемая user-facing IA — пять верхнеуровневых пунктов вместо восьми:

1. `Обзор` — dashboard, last session, sync status, one entry to continue/new session.
2. `Сессия` — active Session/Photo Wizard; это единственное место запуска pipeline.
3. `История` — Sessions with Results and RESERVE as filters/tabs/status views, not separate competing top-level destinations.
4. `Карта` — map review for current session, with optional historical session selector.
5. `Настройки` — global processing/provider/privacy/preferences.

`Результаты` becomes the final wizard state and a tab inside a stored session. `Резерв` becomes a filter/queue inside History and session review. `Журнал` becomes a contextual Diagnostics tab/drawer for the active or selected session, with a dashboard shortcut only when errors exist. This reduces global navigation without removing capabilities.

## 9. Proposed AppShell/navigation

Desktop: persistent left rail with five items, compact session context in TopBar (`№`, title, sync state), one global alert slot, one processing progress slot and content breadcrumb. Keep footer/build diagnostics out of the primary working rhythm.

Mobile: compact TopBar with menu, short screen title, session status chip and progress; drawer contains five items plus a contextual `Текущая сессия` section. Close the drawer with focus return, trap focus while open, use `aria-modal`, remove hidden navigation from tab order, and keep one navigation landmark. Notices should be consolidated and offset below TopBar.

Within History use segmented tabs/chips: `Все`, `Результаты`, `RESERVE`, `Диагностика`. Within a session use a local subnavigation: `Фото`, `Карта`, `Результат`, `Журнал`; it should not compete with global navigation.

## 10. Proposed Session/Photo Wizard

Оптимально оставить четыре шага, но сделать их реальными gated states с одной primary action per step:

| Шаг | Содержимое | Primary | Secondary | Conditional |
| --- | --- | --- | --- | --- |
| 1. Выбор | session metadata, files/folder, count, thumbnails, privacy explanation | `Продолжить к распознаванию` | `Выбрать фотографии`, `Выбрать папку`, `Параметры проверки` | cancel folder import, replace selection, restore draft |
| 2. Распознавание | OCR/EXIF progress, index/coordinate review, quality and manual corrections | `Продолжить к проверке` | `Запустить OCR`, `Назад`, save correction | `Подтвердить координату`, edit index, swap lat/lon, retry failed photo |
| 3. Проверка | map, threshold, conflicts, ACTIVE/RESERVE, cleanup preview | `Подготовить очищенные фото` | `Назад`, `Открыть карту`, `Принять рекомендации` | resolve conflict, move to RESERVE/ACTIVE, fix missing/low precision, cleanup retry |
| 4. Результат | upload status, links, export and session persistence | `Сохранить результат` or `Загрузить очищенные` when provider is valid | `Назад`, `GPX`, `KML`, `GeoJSON`, `TXT`, copy/share | provider fallback/retry, unsynced retry, clear session with explicit scope |

`Только OCR`, `Очистить metadata` and `Загрузить очищенные` remain available as advanced actions, but move under step-specific overflow/secondary menu and must not compete with the step primary. Future steps stay disabled until prerequisites are met, while a completed step remains editable.

## 11. Separate mobile composition

- One short step title, session status chip and one sticky bottom primary action with safe-area padding.
- Metadata fields collapsed behind `Сведения о сессии`; photo selection and count stay above the fold.
- Photo rows use compact cards: thumbnail, index, coordinate/quality status, one visible primary contextual action; details/edit/share/reserve/delete in an overflow sheet.
- Progress is a compact sticky summary that expands to per-photo details; avoid repeating all ten metrics above every card.
- Results use grouped `Экспорт`, `Поделиться`, `Копировать`, `Опасная зона` actions; text blocks collapsed by default.
- Map uses full-screen map plus draggable bottom sheet with visible handle, snap points and `Развернуть список`; only one nested scrolling region.
- Settings and Journal use accordion sections and persistent section summaries; diagnostics remain on demand.
- Drawer uses five global destinations and a separate current-session context; it must not duplicate the desktop rail in the accessibility tree.

## 12. What is safe to replace with Ant Design/ProComponents

Safe presentation candidates: layout/grid/space, buttons, inputs, selects, checkboxes, cards, statistics, tags/status chips, alerts, steps, filters, drawers, modals, tooltips, empty/loading/error states, table shell and design tokens/theme. A responsive table can use Ant Table only if the domain action model and mobile PhotoCard remain explicit.

Keep custom or domain-bound: UploadDropzone and folder capability logic, PhotoCard details/editor, PhotoViewerModal gesture behavior, Leaflet MapPanel/model, progress event bridge, privacy notices, provider chain controls, session restore/migration/diagnostics and all pipeline/export/storage modules. ProTable should not become the source of truth for mobile photo actions or domain state.

## 13. Recommended first implementation scope

First implementation PR should be a narrow presentation slice:

1. Introduce tokens and AppShell/navigation contract with five destinations, consolidated remote notice and accessible mobile drawer.
2. Refactor only Session Wizard/Upload surface into four gated visual states, preserving existing handlers and pipeline calls.
3. Establish one canonical photo action model and render it in desktop table/mobile card without removing functionality.
4. Add mobile sticky primary action, compact progress and map bottom-sheet affordance.
5. Run the existing build/unit/browser suites plus desktop and 360/390/412 screenshots; report backend/provider/physical-device gaps separately.

Do not include in that PR: backend/API/auth/D1 changes, new providers, map engine replacement, data model rewrite, cleanup of legacy files without coverage proof, or a broad Settings redesign.

## 14. Risks and open questions

- Is `pilot/ant-design-ui-v1` expected to remain a visual pilot with local fallback, or must the first UI PR also demonstrate live D1 sync? This changes acceptance evidence.
- Should RESERVE be a global operational queue or only a per-session status? The proposed History filter assumes both views are needed.
- Which upload provider labels/order are product-canonical, and should a failed fallback be visible per photo or only at session level?
- Is `Загрузить очищенные` permitted before manual confirmation of low-precision/suspicious coordinates? Current upload rules allow some non-blockers; the wizard needs a clearly documented gate.
- What is the canonical destructive scope: current photo batch, current result, local session, or remote D1 record? Copy must state this before consolidating clear actions.
- What are the supported real devices/browsers for directory picker, touch gestures, zoom, low-memory large batches and TalkBack?
- What tile fallback/performance/legal behavior is required when map tiles or Leaflet fail?
- Should restore after reload restore only session metadata/thumbnails, or must the product provide a resumable source-file re-selection flow?
- What completion signal is required for provider upload and D1 sync before a result is considered shareable?

## 15. Audit conclusion

The current pilot has a functional and test-covered domain core with a readable dark CRM shell, but the information architecture is broader than the user task and the wizard is primarily a visual navigation layer over one long Upload screen. The highest-value, lowest-risk UI work is to consolidate navigation, make the four wizard states real, establish one action model, and give mobile a sticky primary path while preserving pipeline/privacy/storage/map/export contracts.

No Ant Design refactor or new product UI was implemented in this audit.
